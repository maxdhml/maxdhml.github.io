## Ce que j'ai fait

J'ai conçu, développé et fait évoluer des architectures Web côté client (Front-End) et côté serveur (Back-End) :

* **Front-End & Déploiement statique (`R1.09` / `SAÉ 1.04`) :** Création d'un premier portfolio en HTML5, CSS3 et Bootstrap avec mise en page responsive, validation W3C et déploiement sur GitHub Pages.
* **Back-End & Sécurité Web (`R2.09`) :** Découverte de l'architecture dynamique client-serveur avec Python **Flask** (routage HTTP, templates) et sensibilisation aux vulnérabilités applicatives (**XSS** et **injections SQL**).
* **Progression concrète vers le BUT2 (évolution de ce portfolio & `R3.10`) :** Refonte de mon portfolio en **architecture dynamique découplée** (HTML/CSS/JS vanilla chargeant dynamiquement les fiches Markdown via `fetch()` sur des index JSON `articles.json` générés par script Node.js `generate-index.js`, avec rendu `marked.js` + `highlight.js`) et déploiement en BUT2 d'une application web locale d'administration de données (**pgAdmin4** sous environnement Python isolé en `R3.10`).

## Comment

1. **Séparation des responsabilités :** Structuration du HTML sémantique, feuilles de style dédiées (`style.css`, `editor.css`), et chargement asynchrone des données (`fetch()`).
2. **Inspection & débogage :** Contrôle des requêtes réseau, codes HTTP et DOM via les DevTools navigateur et respect de la portabilité des chemins relatifs sur GitHub Pages.

## Pourquoi

* **Pourquoi être passé d'un site purement statique/Bootstrap à une architecture Markdown + JSON sur GitHub Pages ?** Éditer directement du HTML dupliqué pour chaque nouveau projet ou AC devient vite lourd et source d'erreurs. Stocker le contenu dans des fichiers `.md` indépendants générant automatiquement un index `articles.json` via Node.js (`generate-index.js`) sépare complètement les **données** de la **présentation**, facilite la maintenance sur GitHub Pages (hébergement statique gratuit sans serveur Flask requis) et améliore la réactivité.

## Mes difficultés

* **Ce qui a fonctionné vs ce qui a bloqué :**
  - *Ce qui a fonctionné :* Le passage aux grilles responsives et l'architecture dynamique Markdown/JS du portfolio actuel.
  - *Erreurs et difficultés identifiées :*
    1. **Spécificité CSS & Bootstrap (`SAÉ 1.04`) :** Surcharger Bootstrap sans comprendre la priorité des sélecteurs rendait certaines règles CSS inopérantes, et les breakpoints mobiles cassaient l'affichage d'un CV complet.
    2. **Piège d'architecture sur le viewer (`ac-viewer.html`) :** Sur GitHub Pages (Linux sensible à la casse) et sur un site évoluant vers BUT2, oublier de référencer les nouveaux blocs (`securiser`, `surveiller`) ou cacher tout le bloc dans `portfolio.html` quand `articles.json` est vide rendait les nouvelles sections invisibles.

## Ce que j'en ai appris

* **Progression BUT1 → BUT2 :** En BUT1, je maîtrisais surtout la vitrine HTML/CSS et les bases de routes Flask (`R2.09`). En BUT2, je comprends toute la chaîne Web moderne : séparation client/données (`fetch` + JSON), sensibilisation à la sécurité web (prévention XSS/SQLi, complétée par mes challenges Web **TryHackMe** et **YesWeHack**), et déploiement d'interfaces web d'administration comme `pgAdmin4` (`R3.10`).

## Ce que je ferais autrement

1. **Maquetter et définir le modèle de données (JSON / schéma BDD) avant d'écrire l'interface**, afin d'éviter des refontes CSS/JS en cours de projet.
2. **Conteneuriser mes applications Back-End (`Flask` / `pgAdmin4`) avec Docker** et automatiser la génération/vérification des liens (ex. vérification de casse et d'existence des fichiers `.md` avant `git push`).
